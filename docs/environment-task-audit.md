# Native task audit across the installed kitchens — 2026-11-05

The highest-priority fixes are **rescuing food when plating fails** and **checking that a human can reach a floor delivery before marking it complete**. Both failures reproduce with ordinary task requests and native kitchen state. Three more environments expose concrete gaps in ingredient pickup, dishwashing and handoff planning. The audit changed no gameplay code.

## What ran

Eight isolated, windowless native Overcooked! 2 players were used over the audit. Six covered the installed two-player Party sessions, and two ran focused controls. All ran bridge 0.8.7 from gameplay source `b91e921`, with independent ports, saves and native physics. Each scene load waited for a new generation and a live round; the control session ID was checked before issuing input. P1 received no input in the sweep. Target rate was 60 FPS; the measured first-pass task windows ranged from 34.7 to 56.4 FPS. These are real-time observations, not lockstep trials.

The first pass sampled one `prepare_near_player` request per eligible kitchen from normal spawn. It preferred the nearest offered ingredient supply (109 requests), then an offered empty utensil or plate (19). A six-second discovery window could expire on changing geometry. All 114 completion receipts had the exact item in a fresh native snapshot: 35 on the intended counter, 10 held by P1, 4 on conveyors and 65 loose. A surviving object does not by itself prove the handoff helped P1. The 24 throne-room entries were excluded; the kitchen count includes the tutorial. This is not coverage of every recipe, player role, scripted phase or task in each kitchen.

## Fix queue

1. **Ready food burns while P2 keeps trying to plate it.** In `s_treehouse_2_1`, a normal fetch put one `DLC05_Egg` in a griddle. With `monitor_equipment` running, P2 fetched a plate, then got `placement_unavailable` trying to collect the contents. The recovery reason changed to `processing_not_ready` after the food spoiled. The 55 s run and a fresh 75 s replay both ended with the same griddle still on its burner, the egg `Ruined`, and **nine burning objects**. In `s_keep_3_3`, `take_ready` on `Beef_Roast` similarly stalled collecting from the oven: the original tray was `OverDoing` at 55 s and `Ruined` with one fire in the 75 s replay. The immediate impediments differ. Both expose the same missing decision in [RemoveReady](../src/Plugin/Actions/TaskTakeReady.cs): once P2 commits to a plate, it does not reconsider removing the cookware as the spoil window closes. Recheck the actual transfer interaction, route and remaining time; fall back before spoilage and stop waiting for a transfer that ruined food can no longer satisfy. Evidence: `equipment-matrix/`, `heat-repeat/`.

2. **A shared floor collider can give a false handoff success.** `s_City_H17` reported raw Flour delivered **24.98 units** from P1; `s_Night_3_3` reported Frankfurter delivered **18.08 units** away. Both used `throw_ground_near_player`. Fresh runs reproduced the deliveries at 24.80 and 18.08 units. *After* each successful request, a checked pose fixture placed P2 1.25 units from stationary P1. From the human side, completed route catalogues saw the exact item but never listed it as obtainable. A normal pickup of that item stayed in `destination_unavailable` recovery for 35 s in both kitchens; both items still existed. This tests ordinary walking access from beside P1, not all possible use of cannons or switches. [DropHandoff.Received](../src/Plugin/Actions/DropHandoff.cs) checks the landing collider but does not require a pickup route when a receiving support is supplied. Require a reachable approach for P1 before counting floor delivery. Preserve valid long passes on rafts: 16 first-pass loose landings exceeded five units, but only these two were tested for access. Evidence: `collection/`.

3. **Picking an ingredient backpack can equip the backpack instead.** In `s_treehouse_2_2`, asking for raw Sausage twice led P2 to the advertised source, then failed with `outcome_not_observed` and zero completed steps. The server carrier's back slot contained the exact source backpack. The same mismatch occurred with Flour in `s_campsite_3_1` and with dried fruit in `s_festivemashup_1_3` (initial run and replay). The native `Backpack.CanHandleDispenserPickup` checks the carrier's angle relative to the back of the pack. [Supply discovery](../src/Plugin/Actions/LogisticsInventory.cs) recognizes the spawner, but reaching the object and having a pickup interaction does not establish which interaction will win. Offer and use a stance that dispenses the requested food; distinguish wearing the pack from collecting its contents. Evidence: `backpack-a/`, `backpack-repro/`, `backpack-c/`, `fruit-repro/`. The Bacon probe stalled before pickup and is not counted as this mismatch.

4. **Water-gun kitchens cannot wash dishes autonomously.** `s_resort_1_3` (plates) and `s_resort_1_4` (glasses) each have a native water gun and no conventional sink. A fixture returned one real dirty stack; the catalogue did not offer `wash_dishes`, and direct dispatch returned `task_not_available` in both kitchens, twice. The stacks had `ServerWashable`. Positive control in 1-4: P2 picked up the actual water gun, was staged at the return station's checked approach, and held ordinary Use input for seven seconds. The original dirty glass stack disappeared, the same station contained a `CleanGlassStack`, and the clean-glass count rose from three to four. [WashingAvailable](../src/Plugin/Actions/TaskWashing.cs) requires a `ServerWashingStation`. Add a task path for an obtainable gun, an accessible washable stack and a verified spray stance. Evidence: `wash/`, `wash-repeat/`, `watergun-positive/`.

5. **A rejected ground throw can loop hundreds of times.** In `s_Day_2_1`, raw Raspberry never reached P1 in the 20, 50 or 95 s windows. In the 95 s replay, from 4.92 s onward the same raspberry remained the selected handoff item. The trace entered `unsafe_release_stance` **200 times** for that item, reached 203 internal steps with **zero completed repetitions**, and the final server snapshot still had it in P2's hands. The 50 s replay showed 101 such entries. [The handoff loop](../src/Plugin/Actions/TaskHandoff.cs) remembers rejected counter targets and walking drop approaches; a rejected player-ground throw has neither a counter target nor an excluded release stance here. Remember the rejected plan until the geometry changes, try another feasible delivery, or wait without spending steps on the same rejection. Evidence: `raspberry/`, `raspberry-long/`.

## Additional failures and limits

- **Lost cargo during a walking handoff:** `s_moonfestival_1_1` failed a raw Cucumber request at 19.46 s with `task_observation_unavailable`. The exception was `task_cargo_changed` in `FindHandoff` after walking and settling for a drop; the fresh snapshot had empty P2 hands and did not contain the selected cucumber. The same request succeeded in 10.33 and 7.70 s on two resets. Handle missing cargo on the way to the drop using the existing lost-preparation policy. The trace does not establish what removed the cucumber.
- **Preparation can commit to a board across a divided kitchen:** in `s_campsite_1_1`, P2 picked up a marshmallow and spent the remainder of two 60 s cooked requests trying to place it. A chopped replay isolated the same step: 38.69 s in `destination_unavailable` for the board at `[4.8, 0, -4.8]`. Neither board was in P2's completed spawn route catalogue; the exact marshmallow remained in hand. Cooking was never reached, so this is not evidence of a campfire-fuel bug. Consider deferring that unit before pickup, or parking and rescheduling when the active planner rules out the proposed board. See [board selection](../src/Plugin/Actions/TaskPreparation.cs) and [the provisional route cost](../src/Plugin/Actions/TaskWorld.cs). Evidence: `camp-heat-1/`, `camp-heat-2/`, `camp-trace/`.
- A quiet wait can be right. The plate in `s_balloon_1_5` and the tortilla/plate in `s_courtyard_2_1` / `s_courtyard_2_2` still had no handoff after 60–65 s with P1 stationary. These are candidates for checking teammate cooperation, switches and platform phases; the audit did not establish an executable alternative. Conversely, longer discovery and menu-source probes completed a NuggetChicken handoff in `s_rapids_3_5` and an egg in `s_campsite_2_4`, both originally unprobed. Neither the original non-offer nor a test time limit is a task failure.
- All seven autonomous task types also ran in focused scenarios. The existing [task audit](../scripts/task_audit.py) passed its seven cases: mixed cooking/chopping, ordinary sink washing, firefighting, dirty-dish handoff, burnt-food disposal, equipment monitoring and collecting ready food. Dirty/fire/burnt setup used the documented native fixtures; the dirty handoff also used the documented role swap. Cross-DLC positive controls emptied the original rice pot in `s_Inside_2_3` and discarded the ruined pasta and returned its original pot in `s_battlements_03`. The disposal control still had a fire; its task was disposal, not extinguishing. A separate beach sink probe saw washing offered but got `task_not_available` at dispatch; it is not counted as a successful wash.

## Evidence and replay

The [per-kitchen manifest](environment-task-audit.json) preserves first-pass outcomes separately from follow-ups, plus build hashes, control results and evidence paths. Raw local evidence is under `.local/environment-20261105/`. Each sweep directory contains the catalogue; accepted tasks also have a timestamped trace, final native status and a fresh server snapshot. Focused after-action collection probes used explicit staging **only after** the measured handoff. The first-pass and focused observations were collected on the same gameplay source; each simulator launch built its own DLL.

Start an isolated simulator in the matching DLC. Each invocation below needs a fresh output directory:

```sh
python3 scripts/native_simulator.py --runtime .local/env-replay start --dlc 5 --level s_treehouse_2_1 --port-base 36200
python3 scripts/environment_task_audit.py --runtime .local/env-replay --port-base 36200 --output .local/replay-egg --level s_treehouse_2_1 --probe monitor_equipment --ingredient DLC05_Egg --discovery-seconds 15 --seconds 75
python3 scripts/environment_task_audit.py --runtime .local/env-replay --port-base 36200 --output .local/replay-pack --level s_treehouse_2_2 --ingredient Sausage --seconds 55
python3 scripts/native_simulator.py --runtime .local/env-replay stop
```

Omit `--level` on the audit command to sweep that runtime's entire DLC. For the water gun use DLC 2, `--probe wash --level s_resort_1_4 --discovery-seconds 12`; for the raspberry loop use DLC 8, `--level s_Day_2_1 --ingredient Raspberry --seconds 95`. The runner records task failures and observation limits in each scene's `result.json`. No audit runtime was left running or installed into the interactive game.

To repeat the false-success check, use DLC 8, `--level s_City_H17 --ingredient Flour`. Leave the scene running after the receipt. Record `final.handoff.itemInstanceId`, stage P2 on a supported spot 1.25 units beside P1, and query `available_actions()` again. Match that **same Unity instance ID** in `targets` and `items`; request `pick_up` using its new target ID and inspect both the recovery reason and the server carrier. A newly spawned copy, a different level generation, or a check from the throwing side cannot verify that delivery.
